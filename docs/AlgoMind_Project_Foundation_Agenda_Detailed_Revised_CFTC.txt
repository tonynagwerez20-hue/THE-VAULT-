ALGOMIND
PROJECT FOUNDATION AGENDA
Detailed project foundation, architecture, research and validation specification
Version 1.0 • 4 September 2026
1. Executive Definition
AlgoMind is a hybrid retail trading research and execution system designed to combine market structure, auction/value concepts, order-flow proxies, VWAP, liquidity, imbalance information, news context and—where available—options/dealer-positioning information into a regime-aware decision process. The foundation is deliberately modular so the system can begin with MT5 and Python on a low-resource computer and later accept higher-quality data sources without rewriting the strategy.
The project is not defined as an 'AI bot' first. Its first objective is a deterministic, event-driven market engine that can reproduce the same information and decisions in research, MT5 testing and live operation. Machine learning is an optional decision-quality layer added only after the underlying data, labels, feature timing and execution assumptions have been proven sound.

3. Non-Negotiable Design Principles
No look-ahead: Historical calculations must reproduce what was knowable at each historical instant. Final FVG fill, final swing state, later invalidation or future volume must never leak backward.
One canonical vocabulary: A feature such as VWAP distance, delta proxy or liquidity sweep must have one documented definition and version.
Separate signal from execution: Python may recommend a trade; MQL5 remains the final execution and hard-risk authority.
Proxy honesty: Tick-direction or candle-derived delta is a proxy, not exchange cumulative delta or institutional DOM.
Regime before optimization: The project must establish which market condition exists before selecting the strategy hypothesis.
Complexity earns its place: New data or models are retained only if they produce robust incremental value.
Fail closed: Unknown, stale, malformed or contradictory critical inputs should result in NO_TRADE.
Reproducibility: The same input snapshot and configuration should produce the same deterministic decision.

7. Event-Driven Feature Foundation
The project should move away from static indicator snapshots toward an event-driven model. A feature is not merely a value; for many market concepts it has a lifecycle: created, active, interacted with, filled/mitigated, invalidated or expired.
Event
Required state information
Swing
Creation timestamp, price, direction, confirmation condition, invalidation/retirement state
Liquidity pool
Location, creation time, type, whether swept, sweep time, post-sweep response
FVG/imbalance
Creation time, direction, boundaries, current fill at each timestamp, invalidation state
Delta surge
Start time, rolling magnitude, threshold state, end time
Delta flip
Previous state, new state, transition timestamp
VWAP deviation
Current deviation, maximum deviation known so far, return/rejection state
News event
Scheduled time, release time if known, surprise when released, reaction window
Trade setup
Setup creation time, conditions then present, expiry, execution/invalidity reason
This structure directly addresses the previously identified danger of using final lifecycle values—such as maximum FVG fill—as if they were known on every earlier bar.
8. VWAP, Volume Profile and Value Area
Calculate session VWAP from observations available up to the current timestamp.
Where volume profile is used, define the price-bin method, session boundaries and volume allocation rule.
Record POC, VAH and VAL with their creation/calculation timestamp.
Measure price location relative to VWAP/POC/VAH/VAL in raw price and normalized units such as ATR.
Treat VWAP/value as context rather than a standalone buy/sell trigger.
Use acceptance outside value to support continuation and rejection from value extremes to support mean reversion.
9. Order-Flow and Delta Proxy Foundation
Because ordinary retail MT5 feeds may not provide exchange-grade order flow, AlgoMind should maintain multiple proxy modes. The goal is not to claim institutional accuracy; it is to test whether observable pressure proxies contain useful incremental information.

10. Liquidity and SMC Context
Track observable swing highs/lows and equal-high/equal-low areas.
Track session highs/lows and other objective liquidity references.
Define sweep detection precisely: what price interaction qualifies, over what time window and what confirms/rejects the event.
Use displacement and structure breaks as evidence of directional intent.
Treat FVGs/imbalances as zones with time-dependent state rather than permanent historical facts.
Use order blocks or similar zones only when their creation, validity and invalidation rules are deterministic.
Do not allow later mitigation to change what the feature said before mitigation.
11. Two-Hypothesis Strategy Framework
Hypothesis
Expected environment
Supporting evidence
Do not trade when
Continuation / Trend
Directional expansion and acceptance
Structure break, displacement, value acceptance, persistent pressure, supportive volatility/flow
Breakout repeatedly fails or price returns deeply into value.
Mean Reversion / Balance
Two-sided rotation and stretched price
VWAP/value deviation, sweep, divergence/exhaustion, rejection, return-to-value potential
Strong acceptance outside value or persistent directional expansion.
SMC, order-flow, VWAP, value area, options and news should therefore be treated as evidence streams feeding the hypothesis rather than as unrelated strategies that compete for control.

16. Canonical Decision Message
A conceptual message should contain at least: decision_id, timestamp, symbol, regime, hypothesis, action, confidence, entry/reference zone, stop, target, risk allocation, feature_version, model_version, data_quality, reason_code and expiry.
The schema must include a version number. Any incompatible change should create a new version rather than silently changing historical semantics.
17. Historical Backtest Architecture
Load historical data in chronological order.
Advance a deterministic clock.
At each event, build the information set available at that exact time.
Update event lifecycles without reading future bars.
Build the canonical feature vector.
Classify regime.
Score continuation and mean-reversion hypotheses.
Apply risk and execution assumptions.
Simulate order/fill/position management.
Record every decision, including NO_TRADE decisions.
At the end, calculate returns, drawdown, expectancy, trade distribution and robustness metrics.

19. Live Trading Flow
MT5 receives current broker data.
MQL5 creates a canonical snapshot.
Python updates the feature and regime state.
Python produces trade intent or NO_TRADE.
MQL5 verifies freshness, symbol state, spread, margin, exposure, daily loss and total loss.
MQL5 executes only after its final veto checks pass.
MQL5 manages SL, TP, partial exit and trailing according to the active position policy.
Both engines log the decision and execution result using the same decision ID.

23. Options / Dealer Positioning Layer
When an external options dataset is available, AlgoMind may incorporate strike-level positioning, open interest, implied volatility, dealer gamma estimates and notable flow. The data should be treated as contextual evidence.
Major strikes may act as areas of interest, potential barriers or magnets.
Estimated gamma regime can modify the expected balance-versus-expansion environment.
Options information should not independently trigger a trade without price/structure/flow confirmation.
Every options feature needs a source timestamp and quality flag.
If unavailable, the engine must explicitly set the feature to unavailable rather than substitute invented values.

25. Dataset and Label Governance
Separate raw data, normalized data, derived features and labels.
Version feature definitions.
Use walk-forward rather than random train/test splitting.
Ensure future-based labels are never included in the input feature set.
Store training-window dates and model version.
Include transaction costs in performance labels where appropriate.
Keep an immutable record of the data source used for each experiment.
Use ablation tests to determine whether each information source adds genuine value.

32. Definition of Done
Every trade has a unique decision ID.
Every feature has a definition, unit, source and timestamp.
Every event has a lifecycle rather than a retroactive final state.
Historical features are immune to future-data changes.
Python and MQL5 share the same feature/decision vocabulary.
MQL5 hard risk rules cannot be bypassed by Python.
External data failures produce explicit degraded states.
Backtests include realistic execution assumptions.
Model versions and training windows are recorded.
Walk-forward and out-of-sample results are separated from optimization.
The system can safely stop trading when critical dependencies fail.

35. Final Foundation Position
The strongest foundation for AlgoMind is not to start by building the largest possible trading stack. It is to build a small, deterministic engine whose market information is temporally correct, whose hypotheses are explicit, whose regime selection is auditable, and whose execution is separated from research. That architecture allows the project to begin with zero MQ infrastructure and ordinary MT5 data, then progressively incorporate ZeroMQ, higher-quality order flow, CFTC positioning, options/dealer positioning, news intelligence, databases and ML without changing the underlying strategy contract.
The project's central technical risk is not lack of sophistication. It is false confidence caused by data leakage, unrealistic execution assumptions, proxy-data mislabelling or poor synchronization between research and MT5. Those risks should therefore be treated as first-class foundation requirements.
Appendix — Engineering Rules to Keep Visible
Future information is never a feature.
Final event outcome is never the historical event state.
Proxy delta is labelled as proxy delta.
Options data is labelled by source and timestamp.
Python proposes; MQL5 validates and executes.
Risk controls are independent of model confidence.
NO_TRADE is a valid and often preferred decision.
ZeroMQ is transport, not strategy.
ML is a gate/ranker until proven otherwise.
Every performance claim must survive out-of-sample testing.
